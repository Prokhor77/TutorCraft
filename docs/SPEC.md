## 0. Правила работы для ИИ-агента

1. **Читай ТЗ целиком перед началом**, затем работай строго по этапам из раздела 12. Не реализуй функции следующего этапа, пока текущий не прошёл Definition of Done (раздел 12.2).
2. **Перед каждой задачей** делай короткий архитектурный анализ: какие модули/файлы изменятся, какие зависимости появятся, какие контракты API/БД затрагиваются. Фиксируй его в описании коммита/PR.
3. **Идентификаторы требований.** Каждое требование имеет ID (`FR-COURSE-03`, `NFR-SEC-02`). Ссылайся на ID в коммитах, тестах и комментариях к PR.
4. **Приоритеты:** `P0` — MVP, обязательно; `P1` — версия 1.x; `P2` — дорожная карта. Не делай P1/P2 без явной команды.
5. **Стандарты кода** (обязательны):
   - SOLID, KISS, DRY, YAGNI; классические паттерны — только там, где они упрощают, а не усложняют.
   - Разделение слоёв: данные (репозитории) → бизнес-логика (сервисы/use cases) → интерфейсы (HTTP-контроллеры, UI). Бизнес-логика не знает о HTTP и ORM.
   - Самодокументируемые имена; никаких «магических» чисел и строк — константы, enum, конфигурация.
   - Функции до 20–30 строк, одна ответственность; guard clauses вместо вложенных `if`.
   - Никаких пустых `catch`; все ошибки обрабатываются и логируются.
   - Валидация всех входных данных на границе системы (API, импорт файлов, вебхуки).
   - Логи без чувствительных данных (пароли, токены, ответы на тесты до дедлайна, персональные данные сверх необходимого).
   - Секреты — только через переменные окружения/хранилище секретов; в репозиторий не коммитятся. В репозитории — `.env.example` без значений.
6. **Тесты пишутся вместе с кодом:** unit для доменной логики (оценивание, права, условия доступа), интеграционные для API, e2e для критичных сценариев (раздел 13).
7. **Если требование неоднозначно** — выбери самое простое разумное решение, зафиксируй допущение в `docs/decisions/ADR-XXX.md` и продолжай. Не блокируйся.
8. **Не копируй код, тексты и графику Moodle** (лицензия GPL). Берём идеи и сценарии, реализация — своя.

## 1. Анализ Moodle

### 1.1 Что такое Moodle сейчас

- Open-source LMS на PHP (лицензия GPLv3), существует с 2002 года. Более 50% рынка LMS в Европе, Латинской Америке и Океании; ~21% вузов США.
- Актуальные версии: **5.1** (октябрь 2025), **5.2** (апрель 2026), **5.3 LTS** ожидается в октябре 2026. В 5.2 в ядро добавлены React, дизайн-токены, OpenTelemetry, мульти-проверяющие в заданиях, нативные AI-провайдеры, улучшения навигации по курсу. Это признаки того, что сам Moodle признаёт проблемы UX и пытается модернизироваться — но медленно из-за огромного legacy.

### 1.2 Функциональная карта Moodle (что должно быть покрыто аналогом)

| Область | Возможности Moodle |
|---|---|
| Структура | Категории курсов → курсы → секции/темы (с 4.5 — подсекции) → элементы (activities) и ресурсы |
| Ресурсы | Файл, папка, страница, URL, книга, пояснение (label), IMS content package |
| Активности | Задание (assignment), тест (quiz) с банком вопросов, форум, глоссарий, wiki, семинар (peer assessment), база данных, лекция (lesson, ветвление), опрос/анкета (choice, feedback, survey), чат, H5P, SCORM, внешний инструмент (LTI), BigBlueButton |
| Банк вопросов | ~15 типов вопросов (одиночный/множественный выбор, верно/неверно, короткий ответ, числовой, эссе, на соответствие, drag&drop, вычисляемый, cloze и др.), категории, версии, случайные вопросы |
| Оценивание | Журнал оценок (gradebook) с категориями, весами, формулами, шкалами, рубриками, guide-оценкой, outcomes/компетенциями, экспорт |
| Прогресс | Отслеживание выполнения элементов, условия доступа (restrict access: дата, оценка, выполнение, группа, поле профиля — с логикой И/ИЛИ), завершение курса, бейджи, сертификаты (плагин), компетенции и планы обучения |
| Люди | Роли и права (capabilities, ~600+ прав, контексты с наследованием и переопределением), группы и потоки (groupings), способы записи (вручную, самозапись с ключом, когорты, оплата, гость, мета-курс) |
| Коммуникации | Уведомления (email, web, mobile push), личные сообщения, форумы-объявления, календарь |
| Администрирование | Пользователи, когорты, аутентификация (LDAP, SAML/OIDC через плагины, OAuth2), отчёты (Report Builder), логи, резервные копии курса (.mbz), восстановление, импорт |
| Интеграции | LTI 1.3 (провайдер и потребитель), SCORM 1.2/2004, xAPI (частично), IMS CC, веб-сервисы (REST/SOAP), мобильное приложение |
| Расширяемость | ~2000 плагинов, десятки типов плагинов (mod, block, auth, enrol, qtype, theme, report, local…) |

### 1.3 Сильные стороны (сохраняем идеи)

1. **Гибкость педагогических сценариев**: условия доступа, ветвление, peer review, рубрики.
2. **Мощный банк вопросов** и тесты с попытками, штрафами, случайной выборкой.
3. **Гранулярная модель прав** и контексты (система → категория → курс → элемент).
4. **Стандарты**: LTI, SCORM, IMS CC — совместимость с внешним контентом.
5. **Self-hosting и открытость данных**: организация владеет данными.
6. **Резервное копирование и перенос курса** одним файлом.

### 1.4 Слабые стороны и боли пользователей (что исправляем)

| # | Боль | Кого касается | Как проявляется в Moodle | Наш ответ |
|---|---|---|---|---|
| B1 | **Перегруженные настройки** | Преподаватель | Форма задания/теста — 10–15 сворачиваемых блоков, десятки полей; большинству нужны 3–4 | Прогрессивное раскрытие: «быстрое создание» (3–5 полей) + «расширенные настройки»; разумные значения по умолчанию; шаблоны активностей |
| B2 | **Сложная модель прав** | Администратор | 600+ capabilities, переопределения, конфликты ролей; трудно понять «почему у пользователя нет доступа» | Небольшой набор ролей и прав, сгруппированных по смыслу; инструмент «Объяснить доступ» (почему видит/не видит) |
| B3 | **Устаревший и непоследовательный UI** | Все | Разные паттерны на разных страницах, частые перезагрузки страниц, много кликов | Единая дизайн-система, SPA-подобное взаимодействие, inline-редактирование, drag&drop, автосохранение |
| B4 | **Плохой мобильный опыт** | Студент | Веб-версия плохо адаптирована, мобильное приложение — отдельный продукт со своими ограничениями | Mobile-first адаптивный веб + PWA (офлайн-чтение, push) |
| B5 | **Навигация студента** | Студент | «Что мне сделать сейчас?» — неочевидно; дедлайны разбросаны по курсам | Единая лента «Мои задачи»: что сдать, к какому сроку, что проверено; прогресс-бар в каждом курсе |
| B6 | **Медленная проверка работ** | Преподаватель | Проверка заданий — много переходов между страницами, журнал оценок сложен | Единая очередь проверки («Входящие на проверку») со всех курсов, горячие клавиши, аннотации PDF, быстрые комментарии-шаблоны |
| B7 | **Сложный журнал оценок** | Преподаватель | Формулы, скрытые категории, «естественное» агрегирование — частые ошибки итоговой оценки | Понятная модель: веса категорий + предпросмотр итоговой формулы + предупреждения о некорректной конфигурации |
| B8 | **Тяжёлые обновления и плагины** | Администратор/DevOps | Обновление ломает плагины, долгие миграции | Модульный монолит с версионированным API расширений; миграции без простоя |
| B9 | **Производительность** | Все | Тяжёлые страницы, нагрузка при массовом тестировании | Бюджеты производительности (раздел 8), кэширование, фоновые задачи, горизонтальное масштабирование |
| B10 | **Слабая аналитика** | Преподаватель, методист | Отчёты требуют настройки Report Builder, нет «из коробки» картины риска | Готовые дашборды: вовлечённость, риск отчисления, проблемные вопросы теста |
| B11 | **Уведомления — шум** | Все | Множество писем, сложная настройка | Дайджесты, единый центр уведомлений, настройки по категориям в один экран |
| B12 | **Создание контента** | Преподаватель | Редактор TinyMCE, слабая работа с медиа | Блочный редактор (как Notion): текст, видео, код, формулы, встраивания; вставка изображений из буфера |

### 1.5 Вывод

Строим LMS с **функциональным ядром уровня Moodle** (курсы, активности, банк вопросов, оценивание, условия доступа, роли, стандарты LTI/SCORM), но с принципиально другим подходом к UX: **минимум кликов, разумные умолчания, одна точка входа для каждой роли** («Мои задачи» для студента, «Проверка» для преподавателя, «Здоровье системы» для админа). Функции Moodle, которыми пользуется <5% пользователей (чат, wiki, survey-шаблоны, outcomes), — вынесены в дорожную карту или в плагины.

## 2. Видение продукта и принципы

### 2.1 Цель

Веб-платформа для создания и проведения онлайн-курсов, которую преподаватель осваивает за 15 минут без инструкции, а студент в любой момент понимает, что ему делать дальше.

### 2.2 Модель развёртывания

- **Мультитенантность** (`P0` на уровне модели данных): одна инсталляция обслуживает несколько организаций (tenant). Данные изолированы по `tenant_id`. Возможен и режим single-tenant (self-hosted) — тот же код.
- Сценарии использования: вуз/колледж, корпоративное обучение, онлайн-школа. Специфика сценариев включается настройками tenant, а не форками кода.

### 2.3 UX-принципы (обязательны при проектировании любого экрана)

| ID | Принцип | Проверяемый критерий |
|---|---|---|
| UX-01 | **Прогрессивное раскрытие** | Форма создания любой сущности в режиме по умолчанию — не более 5 полей; остальное в «Дополнительно» |
| UX-02 | **Разумные умолчания** | Активность можно создать, заполнив только название |
| UX-03 | **Автосохранение** | Любой ввод текста длиннее одного поля сохраняется как черновик не реже раза в 10 сек; потеря данных при закрытии вкладки исключена |
| UX-04 | **Inline-редактирование** | Названия, даты, порядок элементов меняются на месте без перехода на отдельную страницу |
| UX-05 | **Глубина ≤ 3 клика** | До любого частого действия (сдать работу, проверить работу, открыть материал) — не более 3 кликов с главной страницы роли |
| UX-06 | **Отмена вместо подтверждения** | Обратимые удаления выполняются сразу с кнопкой «Отменить» (корзина 30 дней), без модального «Вы уверены?» |
| UX-07 | **Объяснимость** | Если элемент недоступен — пользователь видит, почему и что сделать, чтобы открыть |
| UX-08 | **Mobile-first** | Все сценарии студента полностью работают на экране 360px |
| UX-09 | **Доступность** | WCAG 2.2 AA |
| UX-10 | **Единая дизайн-система** | Все экраны собраны из общих компонентов; нет одноразовых стилей |
| UX-11 | **Горячие клавиши** | Для экрана проверки работ и редактора курса; справка по `?` |
| UX-12 | **Пустые состояния обучают** | Каждый пустой список содержит пояснение и основное действие («Создайте первый модуль») |

## 3. Роли и права доступа

### 3.1 Контексты

Иерархия: `Tenant (организация) → Категория → Курс → Модуль курса → Элемент`. Права назначаются в контексте и наследуются вниз.

### 3.2 Системные роли

| Роль | Контекст | Кратко |
|---|---|---|
| `platform_admin` | Вся инсталляция | Управление tenant'ами, глобальные настройки, мониторинг |
| `tenant_admin` | Tenant | Пользователи, категории, интеграции, брендинг, отчёты организации |
| `category_manager` | Категория | Создание курсов и назначение преподавателей в своей категории |
| `teacher` | Курс | Полное управление курсом: контент, участники, оценки |
| `assistant` | Курс | Проверка работ и модерация форумов; не меняет структуру курса. Может быть ограничен группами |
| `student` | Курс | Прохождение курса |
| `observer` | Курс / пользователь | Только чтение прогресса (родитель, руководитель, куратор) |
| `guest` | Курс | Просмотр открытых материалов без выполнения активностей |

### 3.3 Права

- Права сгруппированы в **~40 разрешений** в формате `ресурс.действие` (`course.edit`, `submission.grade`, `grade.export`, `user.impersonate`…). Полный список агент формирует в `docs/permissions.md` на этапе 1 и держит в коде как enum.
- `FR-ACL-01 P0` Роль = именованный набор разрешений. Системные роли неизменяемы; `tenant_admin` может создавать кастомные роли копированием.
- `FR-ACL-02 P0` Проверка доступа — единый сервис авторизации (`can(user, permission, context)`), вызываемый из слоя бизнес-логики. Никаких проверок ролей по имени в контроллерах/UI.
- `FR-ACL-03 P1` Переопределение разрешения роли на уровне конкретного курса/элемента (только разрешить/запретить, без «prohibit»-уровней Moodle).
- `FR-ACL-04 P1` **«Объяснить доступ»**: для пары (пользователь, объект) показать цепочку: роли → контексты → итоговое решение и причину.
- `FR-ACL-05 P1` Режим «Посмотреть как студент» (для teacher) и «Войти как пользователь» (для admin, с записью в аудит и баннером на всех страницах).

## 4. Доменная модель и глоссарий

| Термин | Определение |
|---|---|
| Tenant | Организация, изолированное пространство данных |
| Категория | Древовидная группировка курсов (факультет, отдел) |
| Курс | Контейнер обучения с участниками, структурой и журналом оценок |
| Поток курса (Course run) `P1` | Экземпляр курса с собственными датами и участниками, созданный из шаблона |
| Модуль | Секция курса (неделя, тема). Допускает один уровень вложенности (подмодуль) |
| Элемент (Item) | Единица содержимого модуля: материал (Resource) или активность (Activity) |
| Материал | Страница, файл, видео, ссылка, встраивание — нечего сдавать |
| Активность | Элемент с действием студента и, опционально, оценкой: задание, тест, форум, опрос, LTI, SCORM, H5P |
| Запись (Enrollment) | Связь пользователь–курс–роль со статусом и сроками |
| Группа | Подмножество участников курса; Набор групп (Grouping) — набор групп для конкретной активности |
| Попытка (Attempt) | Одно прохождение теста |
| Ответ (Submission) | Сданная работа по заданию |
| Оценка (Grade) | Результат по элементу оценивания в журнале |
| Условие доступа | Правило, определяющее видимость/доступность элемента |
| Выполнение (Completion) | Статус «выполнено» по элементу или курсу |

## 5. Функциональные требования

Формат: `ID Приоритет` — требование. Критерии приёмки для ключевых требований — в разделе 13.

### 5.1 Аутентификация и профиль (AUTH)

- `FR-AUTH-01 P0` Вход по email + пароль. Хранение пароля — только стойкий адаптивный хеш (argon2id или эквивалент). Политика пароля настраивается tenant'ом.
- `FR-AUTH-02 P0` Восстановление пароля по одноразовой ссылке (TTL 1 час, одноразовая, хранится хешем).
- `FR-AUTH-03 P0` Защита от перебора: ограничение попыток входа по аккаунту и IP, прогрессивная задержка.
- `FR-AUTH-04 P0` Сессии: короткоживущий access-токен + ротируемый refresh-токен в httpOnly Secure SameSite cookie; отзыв всех сессий пользователя.
- `FR-AUTH-05 P1` SSO: OpenID Connect и SAML 2.0 (настраиваются tenant_admin), JIT-создание пользователя с маппингом атрибутов.
- `FR-AUTH-06 P1` Двухфакторная аутентификация (TOTP), обязательная для админ-ролей по настройке.
- `FR-AUTH-07 P1` Вход по magic link (для корпоративных/онлайн-школ).
- `FR-AUTH-08 P2` LDAP / Active Directory.
- `FR-PROF-01 P0` Профиль: имя, фамилия, email, аватар, часовой пояс, язык интерфейса. Кастомные поля профиля (`P1`) задаются tenant'ом.

### 5.2 Пользователи и организация (USER)

- `FR-USER-01 P0` CRUD пользователей для tenant_admin; поиск, фильтры, приостановка (suspend) без удаления.
- `FR-USER-02 P0` Массовый импорт пользователей из CSV с предпросмотром, валидацией построчно и отчётом об ошибках; опционально — сразу с записью на курсы.
- `FR-USER-03 P0` Приглашение пользователя по email со ссылкой установки пароля.
- `FR-USER-04 P1` Когорты (глобальные группы) для массовой записи на курсы.
- `FR-USER-05 P1` Анонимизация / удаление пользователя по запросу (GDPR/152-ФЗ): персональные данные удаляются, учебные записи обезличиваются.
- `FR-USER-06 P1` Экспорт всех данных пользователя (право на переносимость).

### 5.3 Каталог и курсы (COURSE)

- `FR-COURSE-01 P0` Категории курсов: дерево произвольной глубины, drag&drop перемещение.
- `FR-COURSE-02 P0` Создание курса: обязательное — только название; опционально — краткое имя, категория, обложка, описание, даты начала/окончания, формат.
- `FR-COURSE-03 P0` Структура курса: модули (секции) с одним уровнем подмодулей; элементы внутри модулей. Порядок меняется drag&drop; перемещение между модулями.
- `FR-COURSE-04 P0` Видимость: курс, модуль, элемент могут быть скрыты, опубликованы или запланированы к публикации на дату.
- `FR-COURSE-05 P0` Режим редактирования встроен в страницу курса (без отдельного «Включить редактирование»): преподаватель видит элементы управления всегда, студент — нет.
- `FR-COURSE-06 P0` Дублирование элемента, модуля, курса.
- `FR-COURSE-07 P0` Корзина: удалённые курсы/модули/элементы восстанавливаются 30 дней (срок настраивается).
- `FR-COURSE-08 P1` Шаблоны курсов; создание курса из шаблона.
- `FR-COURSE-09 P1` Потоки курса (course runs): один шаблон контента — несколько запусков с разными датами/участниками; сдвиг всех дат при создании потока.
- `FR-COURSE-10 P1` Экспорт/импорт курса в собственный формат (архив: JSON-манифест + файлы), с опцией «с данными студентов / без».
- `FR-COURSE-11 P1` Каталог курсов для студентов с поиском, фильтрами по категории/тегам и самозаписью.
- `FR-COURSE-12 P2` Импорт курса из Moodle-бэкапа `.mbz` (структура, материалы, банк вопросов, тесты, задания; без пользовательских данных). Неподдерживаемые элементы — в отчёте импорта.
- `FR-COURSE-13 P2` Импорт IMS Common Cartridge.

### 5.4 Запись на курс и группы (ENROL)

- `FR-ENROL-01 P0` Ручная запись преподавателем/админом: поиск пользователей, массовое добавление, роль, даты начала/окончания доступа.
- `FR-ENROL-02 P0` Самозапись: вкл/выкл, опциональный код доступа, лимит мест, срок записи.
- `FR-ENROL-03 P0` Ссылка-приглашение на курс (с TTL и лимитом использований).
- `FR-ENROL-04 P0` Статусы записи: активна, приостановлена, завершена. Приостановленный теряет доступ, данные сохраняются.
- `FR-ENROL-05 P0` Группы: CRUD, ручное распределение, автоматическое (случайно по N групп / по N человек), импорт из CSV.
- `FR-ENROL-06 P0` Групповой режим на уровне курса/активности: нет групп / видимые группы / изолированные группы.
- `FR-ENROL-07 P1` Наборы групп (groupings) для активностей.
- `FR-ENROL-08 P1` Синхронизация записи с когортами.
- `FR-ENROL-09 P2` Платная запись (интеграция с платёжным провайдером через абстракцию `PaymentGateway`), промокоды.

### 5.5 Контент и материалы (CONTENT)

- `FR-CONTENT-01 P0` **Блочный редактор** для страниц, описаний, заданий, постов форума: заголовки, текст с форматированием, списки, цитаты, код с подсветкой, формулы (LaTeX), таблицы, изображения, файлы, видео, встраивание (iframe из белого списка доменов), callout-блоки. Хранение — структурированный JSON-документ; рендер в безопасный HTML (санитизация на сервере).
- `FR-CONTENT-02 P0` Вставка изображений из буфера и drag&drop файлов в редактор.
- `FR-CONTENT-03 P0` Типы материалов: Страница, Файл (с предпросмотром PDF/изображений/видео/аудио в браузере), Ссылка, Папка файлов, Видео (загрузка или embed).
- `FR-CONTENT-04 P0` Хранилище файлов: объектное хранилище через абстракцию `FileStorage`; дедупликация по хешу содержимого; лимиты размера на tenant/курс/файл; проверка MIME по содержимому, а не по расширению.
- `FR-CONTENT-05 P1` Антивирусная проверка загрузок (через адаптер, асинхронно; файл недоступен до проверки).
- `FR-CONTENT-06 P1` Видео: транскодирование в адаптивный поток, субтитры (загрузка VTT), отслеживание просмотра для условия выполнения «просмотрено ≥ N%».
- `FR-CONTENT-07 P1` Книга — многостраничный материал с оглавлением.
- `FR-CONTENT-08 P1` Глоссарий курса.
- `FR-CONTENT-09 P2` Встроенная поддержка H5P-контента.
- `FR-CONTENT-10 P2` Версионирование страниц с просмотром истории изменений.

### 5.6 Задания (ASSIGN)

- `FR-ASSIGN-01 P0` Создание: название (обязательно), описание, срок сдачи, способ сдачи (файлы / текст онлайн / оба / без сдачи — офлайн-оценка), максимальный балл. Остальное — «Дополнительно».
- `FR-ASSIGN-02 P0` Дополнительные настройки: дата открытия, жёсткая дата закрытия (после неё сдача невозможна), допустимые типы и число файлов, лимит размера, повторная сдача (сколько попыток), групповая сдача, необходимость нажать «Отправить на проверку» (черновик vs финал).
- `FR-ASSIGN-03 P0` Индивидуальные продления срока для студента/группы.
- `FR-ASSIGN-04 P0` Студент: загрузка файлов с автосохранением черновика, статус (не сдано / черновик / сдано / сдано с опозданием / проверено / возвращено на доработку), просмотр оценки и отзыва.
- `FR-ASSIGN-05 P0` **Экран проверки**: слева список ответов (фильтры: не проверено, опоздание, группа), в центре — ответ студента с предпросмотром, справа — оценка и отзыв. Переход к следующему ответу — без перезагрузки, горячие клавиши (`J/K` — след./пред., `Ctrl+Enter` — сохранить и далее).
- `FR-ASSIGN-06 P0` Отзыв: текст (блочный редактор), файлы, возврат на доработку.
- `FR-ASSIGN-07 P0` Публикация оценок: сразу или вручную пакетно («Опубликовать все оценки»), чтобы студенты не видели частичных результатов.
- `FR-ASSIGN-08 P1` Аннотирование PDF прямо в браузере (выделение, комментарии, рисование); сохранение аннотированной копии.
- `FR-ASSIGN-09 P1` Рубрики (критерии × уровни с баллами) и библиотека рубрик tenant'а; быстрые комментарии-шаблоны.
- `FR-ASSIGN-10 P1` Анонимная (слепая) проверка.
- `FR-ASSIGN-11 P1` Несколько проверяющих с агрегированием (среднее / максимум / согласование модератором).
- `FR-ASSIGN-12 P1` Массовая выгрузка ответов архивом и загрузка отзывов архивом.
- `FR-ASSIGN-13 P2` Взаимное оценивание (peer review): распределение работ, оценка по рубрике, оценка качества рецензий.
- `FR-ASSIGN-14 P2` Проверка на заимствования через адаптер внешнего сервиса.

### 5.7 Банк вопросов и тесты (QUIZ)

**Банк вопросов**

- `FR-QBANK-01 P0` Банк вопросов на уровне курса, `P1` — общий банк на уровне категории/tenant'а с правами доступа.
- `FR-QBANK-02 P0` Папки (категории) вопросов, теги, поиск по тексту, фильтры по типу/тегу.
- `FR-QBANK-03 P0` Типы вопросов MVP: одиночный выбор, множественный выбор (с политикой частичных баллов), верно/неверно, короткий ответ (несколько правильных вариантов, регистр, шаблоны `*`), числовой (с допуском), эссе (ручная проверка), на соответствие, на упорядочивание.
- `FR-QBANK-04 P1` Типы вопросов P1: заполнение пропусков (cloze), drag&drop в текст, drag&drop на изображение, вычисляемый (формула с переменными), выбор пропущенных слов.
- `FR-QBANK-05 P0` Версионирование вопросов: правка создаёт новую версию; существующие попытки ссылаются на версию, в которой были выполнены.
- `FR-QBANK-06 P0` Предпросмотр вопроса «как студент» с проверкой ответа.
- `FR-QBANK-07 P1` Импорт/экспорт вопросов: GIFT, Moodle XML, `P2` QTI 2.1/3.0. Импорт с предпросмотром и отчётом об ошибках.
- `FR-QBANK-08 P1` Статистика по вопросу: индекс трудности, дискриминации, распределение ответов.

**Тест**

- `FR-QUIZ-01 P0` Создание: название, окно доступности (открытие/закрытие), ограничение времени, число попыток, метод итоговой оценки (лучшая / последняя / средняя / первая), проходной балл.
- `FR-QUIZ-02 P0` Состав: вопросы из банка вручную и/или случайные N вопросов из папки/по тегу; перемешивание вопросов и вариантов ответа; разбиение по страницам.
- `FR-QUIZ-03 P0` Прохождение: автосохранение каждого ответа на сервере, навигация по вопросам, пометка «вернуться позже», таймер с серверной валидацией (истечение времени фиксирует сервер, а не клиент), восстановление попытки после обрыва связи.
- `FR-QUIZ-04 P0` Автопроверка при завершении; эссе — в очередь ручной проверки (общую с заданиями, см. FR-GRADE-06).
- `FR-QUIZ-05 P0` Настройка показа результатов: что и когда видит студент (балл, правильность, правильные ответы, отзыв) — сразу после попытки / после закрытия теста / никогда.
- `FR-QUIZ-06 P0` Индивидуальные исключения: доп. время, доп. попытки, иные даты для студента/группы (например, для людей с ОВЗ).
- `FR-QUIZ-07 P0` Отчёт преподавателя: таблица попыток, ответы по вопросам, ручная перепроверка/переоценка всех попыток после исправления ключа.
- `FR-QUIZ-08 P1` Адаптивный режим (несколько попыток ответа на вопрос со штрафом), отзывы на варианты ответа.
- `FR-QUIZ-09 P1` Пароль на тест, ограничение по IP-подсетям, задержка между попытками.
- `FR-QUIZ-10 P2` Интеграция с безопасным браузером / прокторингом через адаптер.

### 5.8 Коммуникации: форумы, объявления, сообщения (COMM)

- `FR-FORUM-01 P0` Форум: темы, ответы с вложенностью (дерево до 3 уровней, далее плоско), блочный редактор, вложения, упоминания `@user`.
- `FR-FORUM-02 P0` Типы: обычный, Q&A (студент видит чужие ответы после своего), объявления (пишет только преподаватель, пост дублируется в уведомления).
- `FR-FORUM-03 P0` Подписка на форум/тему, отметка прочитанного, закрепление, блокировка темы.
- `FR-FORUM-04 P0` Правка своего поста в течение настраиваемого времени; модерация (скрыть, удалить, переместить).
- `FR-FORUM-05 P1` Оценивание участия в форуме (баллы за посты или рубрика по всему вкладу студента).
- `FR-FORUM-06 P1` Реакции на посты, отметка «лучший ответ» в Q&A.
- `FR-MSG-01 P1` Личные сообщения 1:1 и групповые чаты курса; настройка tenant'ом (кому можно писать).
- `FR-NOTIF-01 P0` Центр уведомлений в интерфейсе + email. События: новый элемент, приближение дедлайна (за 24 ч и за 1 ч — настраивается), оценка опубликована, ответ в подписанной теме, объявление.
- `FR-NOTIF-02 P0` Настройки уведомлений пользователя — один экран: строки = категории событий, колонки = каналы.
- `FR-NOTIF-03 P1` Дайджест (ежедневный) вместо отдельных писем; web push (PWA).
- `FR-NOTIF-04 P0` Отправка уведомлений только через очередь фоновых задач, с идемпотентностью (одно событие — одно уведомление на канал).

### 5.9 Опросы и обратная связь (SURVEY)

- `FR-SURVEY-01 P1` Голосование (choice): один/несколько вариантов, лимит на вариант, показ результатов.
- `FR-SURVEY-02 P1` Анкета (feedback): конструктор вопросов (шкалы, выбор, текст), анонимность, сводка ответов с графиками, экспорт CSV.

### 5.10 Условия доступа и выполнение (PROGRESS)

- `FR-PROG-01 P0` Отслеживание выполнения элемента: вручную студентом, автоматически по условиям (просмотрено, сдано, получена оценка, получена проходная оценка, опубликован пост, `P1` просмотрено видео ≥ N%).
- `FR-PROG-02 P0` Условия доступа к элементу/модулю: дата с/по, выполнение другого элемента, оценка по элементу в диапазоне, принадлежность группе. Логика: список условий с «все/любое»; `P1` — вложенные группы условий.
- `FR-PROG-03 P0` Режим недоступного элемента: скрыт полностью или показан с замком и пояснением «Откроется, когда: …» (UX-07).
- `FR-PROG-04 P0` Движок условий — отдельный доменный модуль с чистыми функциями `evaluate(conditions, userContext) → {available, reasons[]}` и 100% покрытием unit-тестами.
- `FR-PROG-05 P0` Завершение курса: по набору обязательных элементов и/или итоговой оценке; дата завершения фиксируется.
- `FR-PROG-06 P1` Сертификаты: шаблоны (фон, поля-плейсхолдеры), генерация PDF при завершении курса, уникальный код и публичная страница проверки подлинности.
- `FR-PROG-07 P1` Бейджи (Open Badges 3.0-совместимые) по завершению элемента/курса.
- `FR-PROG-08 P2` Компетенции и траектории обучения.
- `FR-PROG-09 P2` Геймификация: баллы опыта, уровни, таблица лидеров (отключаемо).

### 5.11 Журнал оценок (GRADE)

- `FR-GRADE-01 P0` Журнал курса: строки — студенты, столбцы — оцениваемые элементы; фиксированные заголовки, фильтр по группе, поиск.
- `FR-GRADE-02 P0` Категории оценивания с весами (например, «Задания 40%, Тесты 60%»), итоговая оценка курса. Агрегирование: взвешенное среднее, сумма баллов, `P1` — отбрасывание N худших.
- `FR-GRADE-03 P0` **Предпросмотр формулы итоговой оценки** человеческим языком и предупреждения о проблемах (сумма весов ≠ 100%, пустая категория, элемент с max=0).
- `FR-GRADE-04 P0` Ручное изменение оценки прямо в ячейке (с журналом изменений: кто, когда, было/стало) и блокировка оценки от автоматического перезаписывания.
- `FR-GRADE-05 P0` Шкалы (буквенные/словесные: «зачёт/незачёт», «отлично…неудовлетворительно») и таблица перевода процентов в буквенную/словесную оценку, настраиваемые на уровне tenant/курса.
- `FR-GRADE-06 P0` **Единая очередь проверки преподавателя** («Входящие»): все непроверенные ответы заданий, эссе в тестах и оцениваемые форумы со всех курсов преподавателя, сортировка по сроку.
- `FR-GRADE-07 P0` Экспорт журнала CSV/XLSX; `P1` — импорт оценок из CSV с предпросмотром.
- `FR-GRADE-08 P0` Студент видит «Мои оценки»: по курсу и сводно по всем курсам, с отзывами и текущей итоговой (с учётом только опубликованного).
- `FR-GRADE-09 P1` Штрафы за опоздание (процент за день/до минимума) — автоматически при расчёте.
- `FR-GRADE-10 P1` Ведомость/зачётная ведомость для вуза: фиксация итоговых оценок за период с подписью (блокировка изменений) и выгрузкой PDF.

### 5.12 Календарь и «Мои задачи» (DASH)

- `FR-DASH-01 P0` **Главная студента «Мои задачи»**: ближайшие дедлайны (со всех курсов, группировка: просрочено / сегодня / на этой неделе / позже), недавно проверенное, продолжить обучение (последний открытый элемент в каждом курсе), прогресс по курсам.
- `FR-DASH-02 P0` **Главная преподавателя**: счётчик «на проверку» по курсам, ближайшие дедлайны в его курсах, студенты в зоне риска (`P1`), последние посты форумов.
- `FR-DASH-03 P0` Календарь: события курсов (дедлайны, открытие/закрытие), личные события; вид месяц/неделя/список; экспорт iCal-подпиской по секретной ссылке (с возможностью перевыпуска).
- `FR-DASH-04 P1` Главная админа tenant'а: активные пользователи, курсы, хранилище, ошибки интеграций, фоновые задачи.

### 5.13 Отчёты и аналитика (REPORT)

- `FR-REPORT-01 P0` Прогресс курса: матрица студент × элемент (выполнено/нет), экспорт.
- `FR-REPORT-02 P0` Журнал событий (аудит): кто, что, когда, откуда, над каким объектом. Фильтры; хранение — настраиваемый срок.
- `FR-REPORT-03 P1` Вовлечённость: последняя активность, время в курсе, доля выполненного; **сигнал риска** (нет входа N дней, пропущены ≥ K дедлайнов, оценки ниже порога) с настраиваемыми порогами.
- `FR-REPORT-04 P1` Аналитика теста (см. FR-QBANK-08) и задания (распределение оценок, % сдавших вовремя).
- `FR-REPORT-05 P2` Конструктор отчётов для админа (выбор сущности, полей, фильтров, группировки) и расписание рассылки отчётов.

### 5.14 Интеграции и стандарты (INTEG)

- `FR-INTEG-01 P0` Публичный REST API (раздел 7) с токенами доступа (personal access tokens и OAuth2 client credentials для сервисов), скоупами и rate limit.
- `FR-INTEG-02 P0` Исходящие вебхуки на доменные события (запись на курс, сдача, оценка, завершение курса) с подписью HMAC, повторными попытками с экспоненциальной задержкой и журналом доставки.
- `FR-INTEG-03 P1` LTI 1.3 Advantage — потребитель (подключение внешних инструментов: Deep Linking, Assignment and Grade Services, Names and Roles).
- `FR-INTEG-04 P1` SCORM 1.2 / 2004: загрузка пакета, плеер, сохранение CMI-данных, передача оценки/выполнения.
- `FR-INTEG-05 P2` LTI 1.3 — провайдер (публикация наших курсов во внешних LMS).
- `FR-INTEG-06 P2` xAPI: отправка statements во внешний LRS.
- `FR-INTEG-07 P2` Видеоконференции (BigBlueButton / Zoom / Jitsi) через адаптер `ConferenceProvider`: создание встречи как активности, запись посещаемости.

### 5.15 ИИ-функции (AI) — все отключаемы, P1–P2

- `FR-AI-01 P1` Абстракция `AiProvider` (провайдер, модель, ключ настраиваются tenant'ом; ключи хранятся зашифрованно). Ни одна функция не зависит от конкретного провайдера.
- `FR-AI-02 P1` Генерация черновика вопросов теста по тексту материала — вопросы попадают в банк только после подтверждения преподавателем.
- `FR-AI-03 P1` Черновик отзыва на работу по рубрике — преподаватель правит и подтверждает; итоговую оценку ставит человек.
- `FR-AI-04 P2` Ассистент студента по материалам курса (RAG только по контенту курса, со ссылками на источник); режим «не давать готовых ответов на оцениваемые задания».
- `FR-AI-05 P1` Прозрачность: всё, что сгенерировано ИИ, помечается; логируются вызовы (без содержимого персональных данных); tenant может полностью отключить ИИ.

### 5.16 Администрирование (ADMIN)

- `FR-ADMIN-01 P0` Настройки tenant'а: название, логотип, цвета (брендинг через дизайн-токены), язык и часовой пояс по умолчанию, политика паролей, домен.
- `FR-ADMIN-02 P0` Управление tenant'ами для platform_admin: создание, приостановка, квоты (пользователи, хранилище).
- `FR-ADMIN-03 P0` Просмотр фоновых задач: очередь, ошибки, повтор.
- `FR-ADMIN-04 P1` Кастомные домены tenant'ов, настройка email-отправителя.
- `FR-ADMIN-05 P1` Политики: соглашение пользователя/политика конфиденциальности с обязательным принятием и версионированием.

### 5.17 Расширяемость (EXT) — P1

- `FR-EXT-01 P1` Ядро — модульный монолит; каждый тип активности реализован как модуль с единым контрактом `ActivityType` (схема настроек, валидация, рендер студента/преподавателя, расчёт оценки, условия выполнения, экспорт/импорт). Новые типы активностей добавляются без изменения ядра.
- `FR-EXT-02 P1` Внутренняя шина доменных событий; модули подписываются на события, а не вызывают друг друга напрямую.
- `FR-EXT-03 P2` Сторонние расширения — через внешние интеграции (LTI, вебхуки, API, UI-встраивания в iframe-слоты), а не через исполнение чужого кода внутри ядра (безопасность и обновляемость, см. боль B8).

**Обязательные инварианты данных**

- `DATA-01` Любой запрос к бизнес-данным фильтруется по `tenant_id` на уровне репозитория (не на уровне контроллера); тест на изоляцию tenant'ов обязателен.
- `DATA-02` Попытка теста ссылается на `QuestionVersion`, а не на `Question` — правка вопроса не меняет прошлые результаты без явной переоценки.
- `DATA-03` `AuditLog` и `GradeHistory` — только вставка, без update/delete (кроме удаления по сроку хранения).
- `DATA-04` Настройки активности (`Item.settings`) валидируются схемой соответствующего `ActivityType` при записи.
- `DATA-05` Документы блочного редактора хранятся как JSON с версией схемы документа; при смене схемы — миграция.
- `DATA-06` Даты хранятся в UTC; отображение — в часовом поясе пользователя.

## 7. API

- `API-01 P0` REST, JSON, версия в пути (`/api/v1`). UI использует тот же публичный API (API-first) — никаких скрытых эндпоинтов для UI, кроме BFF-агрегаций, если они нужны для производительности.
- `API-02 P0` Контракт описан в OpenAPI 3.1 и генерируется из кода или код из него — спецификация в репозитории всегда актуальна (проверяется в CI).
- `API-03 P0` Единый формат ошибок (RFC 9457 Problem Details): `type`, `title`, `status`, `detail`, `errors[]` (поле + код ошибки валидации), `traceId`. Внутренние детали (стектрейсы, SQL) клиенту не отдаются.
- `API-04 P0` Пагинация — курсорная (`?cursor=&limit=`, лимит по умолчанию 25, максимум 100); фильтры и сортировка — через явный белый список полей.
- `API-05 P0` Идемпотентность для небезопасных операций с побочными эффектами (сдача работы, завершение попытки, платежи) — заголовок `Idempotency-Key`.
- `API-06 P0` Оптимистичная блокировка при редактировании (`ETag` / `If-Match` или поле `version`) — для настроек курса, активностей, оценок.
- `API-07 P0` Rate limiting по токену/пользователю/IP с заголовками `RateLimit-*`.
- `API-08 P1` Реальное время (уведомления, счётчики «на проверку», новые посты) — через WebSocket/SSE с авторизацией.

## 9. Архитектурные требования (без привязки к стеку)

- `ARCH-01` **Модульный монолит** с чёткими границами модулей (bounded contexts): `identity`, `org`, `courses`, `content`, `enrollment`, `assessment` (assign, quiz, qbank), `communication` (forum, messaging, notifications), `progress`, `gradebook`, `reporting`, `integrations`, `files`, `audit`. Модуль экспортирует публичный интерфейс; доступ к внутренностям и таблицам другого модуля запрещён (проверяется архитектурными тестами/линтером).
- `ARCH-02` Слои внутри модуля: `domain` (сущности, правила, чистые функции) → `application` (use cases, транзакции, авторизация) → `infrastructure` (репозитории, внешние адаптеры) → `interface` (HTTP, события, CLI). Зависимости направлены внутрь.
- `ARCH-03` Внешние сервисы только через интерфейсы-порты: `FileStorage`, `Mailer`, `AntivirusScanner`, `AiProvider`, `PaymentGateway`, `ConferenceProvider`, `VideoTranscoder`, `PlagiarismChecker`. В тестах — in-memory реализации.
- `ARCH-04` Межмодульное взаимодействие для побочных эффектов — через доменные события (outbox-паттерн для гарантированной доставки в очередь).
- `ARCH-05` Конфигурация — через переменные окружения с валидацией при старте; приложение не стартует с некорректной конфигурацией.
- `ARCH-06` Фичефлаги для P1/P2-функций и ИИ-функций на уровне tenant'а.
- `ARCH-07` Фронтенд: дизайн-система (токены + компоненты) в отдельном пакете; бизнес-логика UI отделена от компонентов представления; клиентский кэш данных с инвалидацией по мутациям.
- `ARCH-08` Развёртывание: контейнеризация, один `docker compose up` для локальной разработки со всеми зависимостями и сид-данными; инфраструктура для продакшна — как код.

## 13. Критерии приёмки ключевых сценариев

**AC-1. Изоляция tenant'ов (DATA-01)**
- *Дано* пользователь tenant A с ролью tenant_admin и курс tenant B.
- *Когда* он запрашивает курс B по прямому ID через API.
- *Тогда* ответ 404 (не 403 — не раскрываем существование), событие попадает в аудит.

**AC-2. Быстрое создание задания (UX-01, UX-02, FR-ASSIGN-01)**
- *Дано* преподаватель на странице своего курса.
- *Когда* нажимает «+» в модуле, выбирает «Задание», вводит только название и нажимает «Создать».
- *Тогда* задание создано со значениями по умолчанию (сдача файлом, 100 баллов, без срока, видимость — как у родительского модуля), появляется в модуле без перезагрузки страницы; всего ≤ 3 клика + ввод названия.

**AC-3. Сдача при обрыве сети (NFR-REL-05, FR-ASSIGN-04)**
- *Дано* студент загрузил файл и нажал «Отправить», соединение прервалось.
- *Когда* соединение восстановилось.
- *Тогда* клиент повторил запрос с тем же `Idempotency-Key`, создана ровно одна сдача, время сдачи — время первой успешной обработки сервером, студент видит статус «Сдано».

**AC-4. Серверный таймер теста (FR-QUIZ-03, NFR-SEC-08)**
- *Дано* тест с лимитом 20 минут, студент начал попытку.
- *Когда* клиент изменил локальное время или отправил ответ через 21 минуту.
- *Тогда* сервер отклоняет ответы после `time_due` (с допуском, заданным константой конфигурации), попытка автоматически завершается сервером фоновой задачей, сохранённые ранее ответы оцениваются; правильные ответы до завершения попытки не присутствуют ни в одном ответе API.

**AC-5. Правка вопроса после попыток (DATA-02, FR-QBANK-05, FR-QUIZ-07)**
- *Дано* 30 завершённых попыток, в вопросе ошибка в ключе.
- *Когда* преподаватель исправляет вопрос.
- *Тогда* создаётся новая версия; старые попытки не меняются, пока преподаватель не нажмёт «Переоценить попытки»; после переоценки журнал оценок пересчитан, изменения записаны в `GradeHistory`, студенты получили уведомление (если оценки опубликованы).

**AC-6. Объяснение недоступности (FR-PROG-03, UX-07)**
- *Дано* тест с условием «Задание 1 оценено ≥ 60%», у студента оценка 50%.
- *Когда* студент открывает курс.
- *Тогда* тест показан с замком и текстом «Откроется, когда: оценка за „Задание 1“ не ниже 60% (сейчас 50%)».

**AC-7. Предупреждение в журнале оценок (FR-GRADE-03)**
- *Дано* категории «Задания 40%» и «Тесты 50%».
- *Когда* преподаватель открывает настройку итоговой оценки.
- *Тогда* видит предупреждение «Сумма весов 90%, должно быть 100%» и текстовую формулу «Итог = 0,4 × Задания + 0,5 × Тесты».

**AC-8. Единая очередь проверки (FR-GRADE-06, FR-ASSIGN-05)**
- *Дано* преподаватель ведёт 3 курса, в них 12 непроверенных работ и 4 эссе в тестах.
- *Когда* он открывает «Входящие на проверку».
- *Тогда* видит 16 элементов, отсортированных по сроку; проверяет все подряд клавишами без возврата к списку; счётчик уменьшается в реальном времени.

**AC-9. «Мои задачи» (FR-DASH-01)**
- *Дано* студент записан на 4 курса с дедлайнами: один просрочен, два сегодня, пять на неделе.
- *Когда* открывает главную.
- *Тогда* видит группы «Просрочено (1) / Сегодня (2) / На этой неделе (5)», каждый пункт ведёт прямо в элемент; на экране 360px всё читаемо без горизонтальной прокрутки.

**AC-10. Производительность (NFR-PERF-02)**
- Нагрузочный тест из репозитория: 500 виртуальных студентов проходят тест из 30 вопросов с автосохранением каждые 10 с в течение 30 минут; p95 записи ≤ 400 мс, ошибок < 0,1%, ни один ответ не потерян (сверка по БД).
